# W4-P divergences (save games)

| area | original behaviour | ours | reason | reference |
|---|---|---|---|---|
| Save format | `.dsg` memory dump of the structs, version string `version 109`; the WADs are not recorded | custom DJSV container (header, tagged sections, CRC-32); not compatible with DOS saves (a DOS file is refused with "bad signature") | ADR-013; saves carry more state than the original and must be checkable | g_game.c:G_DoSaveGame, p_saveg.c |
| Extra state saved | only what the DOS game archives | also: the game and misc RNG indices, `target` / `tracer` / `soundtarget` / `attacker` (by thinker index), the order of every sector thing list and blockmap cell, the item respawn queue, body queue, player starts (deathmatch starts are mutated by `G_DeathMatchSpawnPlayer`), `validcount`, `onground`, boss brain targets and the `easy` flag of `A_BrainSpit`, the full `-fast` / Nightmare changes of the state and mobjinfo tables, `sky texture`, the `-respawn` / `-fast` / `-nomonsters` / deathmatch / net-game parameters | a loaded game must continue exactly like the running one (the save/load tests compare it with the uninterrupted run) | p_saveg.c, p_enemy.c, g_game.c |
| Removed objects still referenced | vanilla archives only live mobjs; pointers to freed mobjs dangle and become NULL on load | objects that were removed but are still referenced (a dead target, a tracer, the sound target of a sector, `player->attacker`, the body queue) are saved as "ghost" entries and come back marked removed with no actor id | the trace and the simulation see the same stale object after a load; no dangling pointer exists in Java | p_saveg.c:P_UnArchiveThinkers |
| `gametic` | not archived: loading keeps the running `gametic` | the saved `gametic` is restored | `A_Tracer` and the turbo check depend on `gametic & 3 / & 31`, so a load of the same file must behave the same whenever it is done | g_game.c:G_DoLoadGame |
| Load | `G_DoLoadGame` reads the file, `G_InitNew` loads the map, then the archives are overlaid | same order; the file is fully validated (signature, version, CRC, game mode, map exists, sector/line/side/blockmap sizes) before the running game is touched | "corrupt file: clear error, never a crash" | spec 08 section 2.3 |
| Corrupt or unusable file | `I_Error` ("Bad savegame") ends the program | a message to the player (`Couldn't load game: ...`) and the game goes on; if the failure happens after the running game was replaced the session returns to the title loop | no crash | g_game.c:G_DoLoadGame |
| Different WADs | the save does not record them, a wrong WAD loads and misbehaves | the header records name and SHA-256 of every WAD (hash over lump names, sizes and contents, so a renamed file is the same WAD); a difference gives the HUD message `WARNING: save made with different WADs` and a log line, the load goes on. A save of another game mode (shareware vs commercial ...) is refused | spec 08 section 2.3 | - |
| Different game version | not recorded | recorded; a difference is a warning like different WADs | - | - |
| Save outside a level | `M_SaveGame` only offers saving in a level | the session ignores a `BTS_SAVEGAME` outside `GS_LEVEL` (nothing is written) | robustness against a stale request | g_game.c:G_DoSaveGame |
| Automap | `ML_MAPPED` is a line flag and is archived | not archived: the renderer keeps the seen lines (`MappedLines`) outside the simulation | the simulation does not hold the flag | p_saveg.c:P_ArchiveWorld |
| `player->message`, `cmd` | not archived | not archived (the loaded game starts without a HUD message; a save warning is shown instead) | - | - |
| Save file write (engine) | `M_WriteFile` in place | temp file + atomic move, so a crash keeps the previous save of the slot | robustness | m_misc.c:M_WriteFile |
| Timestamp / description | description only (24 characters) | description (24 characters) and a wall-clock timestamp in the header, taken from a `Clock` injected into the codec | spec 08 section 2.2 | - |
| First save | - | the first save of a session hashes the WADs (about 90 ms for a 27 MB IWAD) on the tic thread; later saves take under 1 ms | simple, once per session | - |
